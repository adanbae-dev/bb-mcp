# 코드 리뷰 5대 원칙

리뷰가 지켜야 할 것. `plugin/skills/bb-pr-review/SKILL.md` 가 이 문서를 구현한다.

**이 문서는 규칙의 단일 소스가 아니다.** 원칙 1·2 는 스킬에 이미 **구체적인 절차로**
들어가 있고, 여기서는 그것에 이름을 붙일 뿐이다. 같은 규칙을 두 곳에 쓰면 한쪽만
고쳐진다(`CLAUDE.md` §4).

---

## 1. 단정하지 않는다

의도를 악의로 읽지 않는다. 확인하지 않은 것을 상상으로 채우지 않는다.

**이미 스킬에 있는 것** — 추측은 `추정:` / `확인 필요:` 로 시작 · 재현 경로를 코드로
완주(「재현 경로를 코드로 완주」) · 호출부를 세지 못한 채 "죽은 코드" 라고 단정하지
않음 · 프레임워크 런타임 동작에 기대는 주장은 근거를 대거나 쓰지 않음.

## 2. 객관적 근거에 기반한다

사실과 추론을 섞지 않는다. 상대가 확인할 수 있게 근거를 붙인다.

**이미 스킬에 있는 것** — `path/to/file.ext:LINE` 인용 · 저장소 규약 파일을 읽고
그 문장을 인용(「저장소 규약 로드」) · base 대조로 "이 PR 의 회귀" 판정
(「회귀인지 대조」) · "일반적으로" · "업계 통상" 금지.

## 3. 전제를 일치시킨다

용어·사양·전제가 다르면 지적의 절반은 오해다.

- 용어나 개념이 PR 과 저장소 규약에서 다르게 쓰이면 **그 차이를 먼저 적는다**
- 사양이 불명확하면 단정 대신 `확인 필요:` 로 **묻는다**
- PR 설명과 코드가 어긋나면 어느 쪽이 맞는지 묻는다. 코드만 보고 설명을 무시하지 않는다

**이 원칙에는 전용 분류가 있다** — 스킬의 `[기록]`. 코드 밖의 기록이 코드와
어긋나는 것은 코드 결함이 아니라서, 분류가 없으면 품질로 눌린다. 실제로 눌렸다.

## 4. 팀이 함께 시스템을 만든다

일관성은 사람 기억이 아니라 구조가 만든다.

- 고정 포맷을 지킨다 — P1/P2/P3/Q 등급 · 「지적 목록」 표 · `### P1-1.` 번호 · `## 종합 의견`.
  답글에서 번호로 지적을 참조할 수 있는 것이 이 고정의 값이다
- PR 설명은 [`pr-template.md`](./pr-template.md) 를 쓴다 — **만드는 쪽의 규약이다.**
  리뷰에서 남의 PR 을 이 템플릿으로 재단하지 않는다
- 규약을 어긴 것이 아니라 **규약이 없어서** 생긴 문제면, 지적 대신 규약 추가를 제안한다

## 5. 솔직하게, 그러나 사람이 아니라 코드에

- 지적은 **코드를 향한다.** "왜 이렇게 했나" 가 아니라 "이 조건에서 이렇게 된다" 로 쓴다
- 감정·사족·완충 표현을 넣지 않는다. 우회해서 말하면 지적이 흐려진다
- **틀렸으면 그 자리에서 정정한다.** 리뷰어의 오판도 리뷰 대상이다

### 사람이 지키는 운영 규칙

스킬이 지킬 수 없어서 여기에만 둔다.

- 승인은 **"미해결 P1 이 없음"** 을 뜻한다. P2·P3 가 남아 있어도 승인할 수 있다
- P1 은 머지를 막는 권한이므로 근거 없이 쓰지 않는다. P1 을 받으면 Bitbucket 에서
  Request changes 를 걸고, 동작이 바뀌는 수정이면 그 항목만 재QA 한다
- P1 에 이견이 있어 코멘트가 두 번 이상 오가면 짧은 통화로 결론을 내고 결과를
  스레드에 한 줄 남긴다. 합의가 안 되면 팀이 정한 결정권자가 정한다
- P2 를 반영하지 않을 때는 사유를 한 줄 남긴다 (예: `범위 밖이라 PROJ-0000 으로 분리`)
